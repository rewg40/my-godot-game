# Инструкция для агента: как вести этот сайт и делать детально проработанные игры на Godot

Документ для ИИ-агента (Arena Agent Mode, Claude/ChatGPT/Gemini и т. п.) и для людей.
Два режима работы: **А. Библия проекта** (сайт, который ты видишь) и **Б. Производство игры на Godot**.

---

## А. Работа с сайтом-библией

### А.1. Где что лежит

| Путь | Что это | Можно ли править |
| --- | --- | --- |
| `game-docs/src/index.html`, `app.css`, `app.js` | сам сайт (SPA без сборки, без npm) | только по явной просьбе |
| `game-docs/src/config.json` | доступы, пути, ветка-источник | да, при смене кодов/ветки |
| `game-docs/src/content/scenario.json` | вкладка «Сценарий» | **да, это основная рабочая зона** |
| `game-docs/src/content/mechanics.json` | индекс подвкладок «Механика» | только при добавлении/удалении подвкладки |
| `game-docs/src/content/mech_*.json` | 13 разделов механики (в т. ч. `mech_physics.json`) | **да** |
| `game-docs/src/content/preview.json` | вкладка «Картинки / превью» | да |
| `game-docs/src/content/images.json` | реестр картинок | да (при добавлении файлов) |
| `game-docs/src/content/models.json` | реестр 3D-моделей | да (при добавлении файлов) |
| `game-docs/src/content/images/**` | сами картинки (≤ 1,5 МБ, WebP/JPG) | да |
| `game-docs/src/content/models/**` | превью-модели GLB/GLTF (≤ 24 МБ) | да |
| `game-docs/src/content/agent-inbox/*.md` | входящие запросы от автора | читать; после выполнения — в `agent-inbox/done/` |
| `game-docs/src/docs/` | текстовые инструкции (этот файл, USAGE.md) | да |
| `.github/workflows/deploy-docs-site.yml` | публикация на GitHub Pages | не трогать без нужды |

### А.2. Как агент получает запрос

1. Автор пишет запрос в чат Arena **или** кидает его в очередь: сайт → «Запросы агенту» → коммит в `game-docs/src/content/agent-inbox/NNNN-slug.md`.
2. Порядок действий агента: `git pull` → прочитать `agent-inbox/` (если просят «разбери inbox») → внести правки в нужный JSON → проверить валидность → коммит → `git push` → сказать автору URL и что именно изменилось.
3. Сайт подхватит изменения сам: GitHub Actions пересоберёт Pages (~40–90 с). Поэтому «агент подключён к сайту» = агент пишет в те же файлы, из которых сайт читает.

### А.3. Формат контента (JSON-схема)

```jsonc
{
  "id": "craft",                    // id подвкладки, совпадает с именем файла
  "kind": "mechanics",              // scenario | mechanics | preview
  "title": "Крафт",
  "subtitle": "одна строка — о чём раздел",
  "status": "wip",                  // draft | wip | done | idea
  "updated": "2026-10-30T21:20:00Z",
  "blocks": [                        // порядок = порядок на странице
    { "type": "note", "text": "врезка-пояснение" },
    { "type": "h",    "text": "Заголовок подраздела" },
    { "type": "p",    "text": ["абзац 1", "абзац 2"] },
    { "type": "list", "ordered": false, "items": ["пункт", "пункт"] },
    { "type": "todo", "items": [{ "text": "открытый вопрос", "done": false }] },
    { "type": "kv",   "head": ["Колонка", "Значение"], "rows": [["a", "b"], ["c", "d"]] },
    { "type": "code", "lang": "gdscript", "code": "func x() -> void:\n\tpass" },
    { "type": "image", "src": "images/preview/concept.png", "caption": "что на картинке" }
  ],
  "glossary": [["термин", "определение"]]   // необязательно
}
```

Правила:
- В строках доступен `**жирный**`, `*курсив*`, `` `код` `` и обычные URL. Никакого HTML.
- В таблицах (`kv`) число ячеек в строке = числу колонок в `head`. Короткие ячейки, длинные мысли — в `list`/`p`.
- Заголовок раздела — отдельный блок `h`; всё, что между `h`, относится к предыдущему заголовку.
- Путь к картинке — относительно `content/` (`images/...`) или полный URL `https://raw.githubusercontent.com/...`.
- После правки — обновить `updated` (UTC, ISO) и не менять `id`.

Проверка перед коммитом (обязательна):

```bash
for f in game-docs/src/content/*.json; do python3 -c "import json,sys; json.load(open(sys.argv[1], encoding='utf-8'))" "$f" || echo "BAD $f"; done
```

### А.4. Стандарт качества записи (чтобы раздел был детальным, а не «пунктиром»)

Каждый раздел механики обязан содержать минимум:
1. **note** — 1–3 предложения: зачем система и какое у неё дизайн-правило.
2. **Концепция** — абзацы: что игрок чувствует, чего система сознательно не делает.
3. **Числа** — таблица (`kv`) с реальными значениями: скорость в м/с, расход в ед./мин, радиусы в метрах, вероятность в %. Числа должны быть согласованы между вкладками (если «бег 6,2 м/с» в «Персонаже», в «Локациях» расстояние в 400 м = ~65 с).
4. **Формулы и правила** — отдельный блок, можно `code`.
5. **Связи** — список «ломает / зависит от»: например, крафт зависит от света (Погода) и веса (Инвентарь).
6. **Реализация на Godot** — блок `code` с конкретными классами/нодами/настройками (Node3D, CharacterBody3D, Resource; имена сигналов и комментарии — на русском).
7. **Бюджет и ограничения** — FPS/память/лимиты (сколько активных объектов, размер LOD).
8. **Открытые вопросы** — `todo`-список, чтобы автор ответил.
9. **MVP vs v1** — что делаем в первую очередь.

Запрещено: «система крафта будет интересной», «нужно проработать», «добавить реализма». Всегда: что именно, сколько, чем измеряется, что будет, если игрок захочет это обмануть.

### А.5. Сценарий: как писать

- Сцены — таблицей: `N | место | время | что видно | реплика/действие | механика | флаг мира`. Флаг мира обязателен: каждая значимая сцена меняет состояние (`set school_mercy=1`).
- Диалоги — реплики ≤ 120 знаков, ключи вида `act1/q1_radio/line_03`; никаких «длинных простыней».
- Персонаж — таблица «хочет / боится / врёт / чего не сделает никогда» + арка по актам.
- Каждый акт — вопрос (что игрок решает), ресурс (чем платит), поворот (что ломает план), награда (что открывается в мире).
- Мотивацию злодея формулировать так, чтобы она была верна с его точки зрения.
- Если автор просит «напиши сцену» — отдавать и в прозу-описание (для людей), и в машиночитаемый блок (`code` с `[SCENE]/[ACTION]/[CHOICE]/[FLAG]`), чтобы потом импортировать в диалоговую систему.

### А.6. Реестр картинок и 3D-моделей

При добавлении файла агент обязан:
1. положить файл в `game-docs/src/content/images/<раздел>/<имя>.webp` (имена: `kebab-case`, без пробелов и кириллицы) или `.../models/<имя>.glb`;
2. сжать картинки до ≤ 1400 px по длинной стороне, ≤ 1,5 МБ (WebP q≈0.82);
3. добавить запись в `images.json` / `models.json`: `id, name, file, caption, tags[], tab, author, date`;
4. `file` — путь относительно `content/` (`images/preview/xxx.webp`);
5. упомянуть файл в нужном разделе блоком `image`, чтобы картинка была в контексте, а не «в галерее где-то».

Модели: не класть в git больше 24 МБ на файл; для «тяжёлых» — ссылка на релиз/архив + запись с `size_mb: null` и примечанием. Если файл больше или это исходник (`.blend`, `.fbx` с текстурами) — писать путь в репозитории, а не дублировать.

### А.7. Доступ и безопасность

- `config.json → gate.allowed` — массив SHA-256 кодов. Новый гость: `python3 -c "import hashlib;print(hashlib.sha256('КОД'.encode()).hexdigest())"` → добавить в `allowed` → коммит.
- Коды — одноразовые, не из личных данных, не совпадающие с паролем от GitHub.
- **Никогда** не коммитить токены, приватные ссылки, «секретные» пути. Токен пользователя живёт только в его localStorage.
- Замок — «от любопытных», а не от атакующего: в статичном сайте обходимо. Для реальных секретов — не в этом репозитории.

## Б. Производство игры на Godot 4.x

### Б.1. Версия и конфигурация

| Параметр | Значение | Почему |
| --- | --- | --- |
| Godot | 4.3+ (stable, не dev) | стабильный 3D + физика, VoxelGI, glTF |
| Renderer | Forward+ (desktop) / Mobile (слабые GPU) | Forward+ нужен для динамических теней и объёмного тумана |
| Физика | `physics/common/physics_ticks_per_second = 60`, `max_steps = 2` | стабильный melee/ragdoll |
| Точки | `1920×1080`, `window/stretch/mode = canvas_items`, `aspect = expand` | UI не «прыгает» на 21:9 |
| Юниты | 1 м, +Y вверх, метрическая система | совпадает с DCC-экспортом |
| Единицы времени | игровые сутки = 24 мин реала (см. «Погода») | одна константа `GameClock.timeScale` |

### Б.2. Архитектура

```
Ostrov/godot/
├── project.godot
├── systems/            # автозагрузка: EventBus, GameClock, SaveMgr, AudioMgr, NoiseBus, Env
├── data/               # .tres-ресурсы: items/, recipes/, quests/, loot/, dialogue/, weather/
├── scenes/
│   ├── boot/           # MainMenu, Loader, Options
│   ├── player/         # Player.tscn (CharacterBody3D) + rig/ + camera/ + stats/
│   ├── world/zones/    # beach/ port/ town/ plant/ cache/ forest/ tunnels/ rock/
│   ├── ai/             # zombie/ npc/ horde_director/ perception/
│   └── ui/             # hud/ inventory/ crafting/ journal/
├── art/ audio/ l10n/ tests/
└── .godot/             # в .gitignore
```

Правила кода (нарушение = переписать):
1. **Данные ≠ логика.** Всё настраиваемое — `Resource` (+`.tres` в git). Никаких магических чисел в скриптах: ни `speed = 6.2`, а `stats.run_speed`.
2. **Тонкие сцены, толстые системы.** Система владеет состоянием и отдаёт сигналы; сцена — только представление.
3. **Связь через типизированные сигналы** (`signal died(part: StringName)`) или `EventBus`. `get_node("../Player")` в рантайме — запрещено; инъекция через экспорт или `@onready` в одном месте.
4. **Fixed tick для симуляции** (0,2 с: нужды, ИИ, лут, погода), 60 Гц — только ввод/камера/анимация. Симуляция обязана быть детерминированной: `RandomNumberGenerator` c seed сохранения, без глобального `randf()`.
5. **Процедурность через seed.** Лут, погода, слухи, состав стад — `hash(save_seed, poi_id, day)`. Один и тот же сейв = один и тот же мир.
6. **Сохранения версионируемые:** `{"version":3,"schema":"zombi.save/v3",...}` + миграции; 1 файл на сегмент, сжатие `Compression.zstd`, checksum от порчи.
7. **Никаких синглтонов-«богов»**, которые знают всё: `GameClock`, `NoiseBus`, `Env` — маленькие и ортогональные.
8. **Проверка допущений сразу:** любая цифра из дизайн-дока обязана иметь в проекте «песочницу» — сцену `tests/sandbox_<system>.tscn`, где её можно подвигать ползунками и посмотреть на результат за 30 секунд.

### Б.3. Шаблон подсистемы (как писать код механики из «Механики» сайта)

```gdscript
class_name NeedsSystem extends Node
## Тик потребностей персонажа. Источник чисел — data/survival/needs_profile.tres

signal need_changed(key: StringName, value: float, prev: float)
signal need_critical(key: StringName, value: float)

@export var profile: NeedsProfile           # .tres: decay/сек, пороги, множители
@export var tick_interval := 0.2
var _acc := 0.0
var _stats: CharacterStats

func setup(stats: CharacterStats) -> void:
    _stats = stats

func _process(delta: float) -> void:
    _acc += delta
    if _acc < tick_interval: return
    var dt := _acc
    _acc = 0.0
    _simulate(dt)

func _simulate(dt: float) -> void:
    var load_mul := MovementState.load_factor()          # 1.0 шаг .. 2.2 спринт
    var weather_mul := Env.snapshot().needs_mul          # холод/жара (см. «Погода»)
    for key in profile.keys():
        var prev: float = _stats.needs[key]
        var next: float = clampf(prev - profile.decay(key) * dt * load_mul * weather_mul, 0.0, 100.0)
        if not is_equal_approx(prev, next):
            _stats.needs[key] = next
            need_changed.emit(key, next, prev)
        if next <= profile.critical(key):
            need_critical.emit(key, next)
```

Что обязано быть у каждой системы: `*_profile.tres` (числа), юнит-тест (gdUnit4) на «крайние» значения, `debug_overlay` (F3) с текущими числами, и запись в README-раздел сайта.

### Б.4. Ключевые Godot-приёмы для зомби-выживача

- **Движение:** `CharacterBody3D` + `move_and_slide()`; `velocity` считается вручную; наклон/лестницы — через `RayCast3D` вниз + `floor_max_angle`.
- **Камера:** `SpringArm3D` (0,6 м) + `Camera3D` 62°; `top_level=false`, `shape` для коллизии со стеной; шейк — через «trauma²», а не прямое смещение.
- **Навигация толпы:** coarse `NavigationRegion3D` (сетка 1 м, `cell_size = 0.5`) + `NavLink3D` для перелазов; у зомби — flow-field к «шуму», у NPC — `NavigationAgent3D` + расписание.
- **Восприятие ИИ:** зрение = 3 `RayCast3D` в конусе на 10 Гц, слух = `NoiseBus` события, обоняние = диффузия по сетке 1 Гц; всё в одном `PerceptionSystem` — чтобы поведение было читаемо и тестируемо.
- **Взаимодействия:** единый `Interactable` (интерфейс `can_interact`, `interact`, `describe`) + `InteractionPicker` (Area3D вокруг игрока). Никаких отдельных `Door.gd`/`Loot.gd` с разным API.
- **Инвентарь:** `ItemRegistry` (id → ItemResource) + `InventoryGrid` (слоты/стек/вес) + операции (move/split/merge/equip) как чистые функции → легко тестировать и сериализовать.
- **Предметы в мире:** `PickupItem` со складыванием (stack) в `ItemContainer`; лут генерится по seed при первом входе в контейнер и больше не меняется.
- **Разрушаемость:** пре-фрактуренные ConvexBody3D-осколки из пула; `RigidBody3D.freeze = true` до момента разрушения; коллизии включаются только в радиусе 20 м от игрока.
- **Огонь/вода:** клеточный автомат на `Image`/массиве 0,5 м, 4 Гц, только активные сегменты; свет и дым — производные, не «отдельная логика».
- **Анимация:** `AnimationTree` (blend-space по скорости) + `AnimationNodeAddList` для «покалывания/тряски/дыхания»; root-motion только у ударов; 25 Гц за пределами 20 м (`AnimationPlayer.speed_scale`).
- **Звук:** автобусы `Master/Music/Sfx/Voices/World/Danger`; все звуки — ещё и событие в `NoiseBus`; реверб — `Area3D` c `ReverbEffect` per-зона.
- **Погода/освещение:** `WorldEnvironment` (fog density, sky material) + `DirectionalLight3D` из `GameClock`; погода — один источник истины `Env`, остальные читают snapshot.
- **Сохранение сегментов:** сегмент = `PackedScene` + `ZoneState` (Resource). При выгрузке сегмента — сериализация его состояния, при загрузке — восстановление (лут, трупы, постройки, флаги).
- **Стриминг:** `ResourceLoader.load_threaded_request` для сегментов; загрузка «за 250 м», выгрузка «за 420 м», игрок никогда не видит pop-in (в это время — «чёрный экран-коридор» или лифт).

### Б.5. Производительность (бюджеты — проверять в CI, а не «на глаз»)

| Метрика | Цель | Как мерить |
| --- | --- | --- |
| Кадр (CPU) | ≤ 13 мс @1080p | `Performance.TIME_FPS`, оверлей F3 |
| Зомби-ИИ суммарно | ≤ 2,5 мс при 60 агентах | `Time.get_ticks_msec()` вокруг `_tick` |
| Draw calls на сегмент | ≤ 2 500 | `RenderingInfo` |
| Память текстур | ≤ 1,6 ГБ | `Performance.RENDER_TEXTURE_MEM_USED` |
| Размер сохранения | ≤ 4 МБ | размер файла сейва |
| Загрузка сегмента | ≤ 400 мс | таймер в `ZoneLoader` |

Приёмы: GPU instancing пропсов, MultiMesh для «толпы без ИИ», imposters с 90 м, атласы текстур, Basis/ETC2, lightmaps для статики, `visible_distance` + LOD-группы, пулы (осколки, трассеры, UI-строки).

### Б.6. Контент-пайплайн

1. Источник: `art/src/*.blend` → экспорт GLB в `game-docs/src/content/models/` (только превью) и в `Ostrov/godot/art/imported/` (рабочие ассеты).
2. Naming: `chr_ / zom_ / prop_ / env_ / wpn_ / veh_ / tex_ / snd_ / anim_` + `_lod1`, `_col`, `_var_a`.
3. Игровые числа — только в `.tres`; импорт из таблиц: `tools/csv2tres.py` (CSV → Resource), CSV живёт рядом с разделами сайта.
4. Локализация: `l10n/ru.csv`, `l10n/en.csv`, ключ = `act/quest/id`; импорт `Translation` в Godot; кириллица в шрифте обязательна (иначе «квадраты» в билде).
5. Архивы в корне репо (`ZOMBI.7z.*`, `остров 1.7z.*`, `персонаж 1.7z.*`) — исходники автора. Распаковывать **только** в рабочую папку, в git не коммитить целиком; превью и манифест — в `game-docs`.

### Б.7. Тесты, сборка, качество

- **gdUnit4** на каждую систему: `tests/unit/test_needs.gd`, `test_crafting_queue.gd`, `test_loot_determinism.gd` (один seed → один лут), `test_save_roundtrip.gd` (сейв → лоад → сейв = идентичен).
- **Headless-смоук** (уже настроен в репо): проект открывается, boot-сцена грузится, 60 тиков без ошибок.
- **Playtest-протокол:** каждые 2 недели — 5 задач на 20 минут, замер «смертей/мин», «минут до первого крафта», «%/время в меню». Правки, не выдержавшие замер — откатывать.
- **Definition of Done для системы:** числа в `.tres` + связка с другими системами + отладочный оверлей + юнит-тест + запись в соответствующей вкладке сайта со статусом `done`.

### Б.8. Чек-лист «детально проработано» (заполнять перед статусом done)

- [ ] Есть измеримые числа и они согласованы с другими вкладками.
- [ ] Описаны крайние случаи: 0 еды, 100 зомби, -25 °C, пустой инвентарь, смерть NPC.
- [ ] Указана цена для игрока и «как обмануть систему» (exploit-лист).
- [ ] Есть связи: «зависит от…», «ломает…».
- [ ] Есть Godot-контур: ноды, сигналы, ресурсы, где лежат данные.
- [ ] Есть бюджет производительности и LOD/пулы.
- [ ] Есть MVP (то, что можно playable за 2 недели) и что откладываем.
- [ ] Есть открытые вопросы автору (todo) — минимум 3.
- [ ] Есть как это тестируется (кейсы gdUnit4 / сценарий плейтеста).

### Б.9. Анти-паттерны (автоматически = переделать)

- «Сначала сделаем красиво, потом оптимизируем» без бюджета с первого дня.
- Одна сцена `World.tscn` на весь остров; `while true` в `_process`; `await get_tree().create_timer()` внутри цикла на 60 агентов.
- Логика крафта в UI-скрипте; лут, генерируемый `randf()` без seed; «менеджеры» на 1 000 строк.
- Дизайн-док без чисел; «реализм» вместо правил; правки сайта без валидации JSON; коммит бинарников > 24 МБ в git без LFS.
- Исправление «на глаз» без записи в `mech_*.json` — через неделю никто не знает, зачем 6,2 м/с.

### Б.10. Формат ответа автора

После любой правки сайта агент отвечает коротко:
1. Что изменено (файлы, разделы, блоки).
2. Какие числа появились и с чем согласованы.
3. Что нужно решить автору (вопросы из `todo`).
4. Ссылка: `https://rewg40.github.io/my-godot-game/#mechanics/<id>` и напоминание, что Pages обновится ~1 минуту.
